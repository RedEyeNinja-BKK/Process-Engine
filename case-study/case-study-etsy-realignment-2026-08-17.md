# Case Study — Etsy Package Realignment Through Process Engine (2026-08-17)

> **What this is:** a recorded downstream use of Process Engine to realign an
> existing Turnstone-native Etsy package with new source material. It is a
> usage, generation, review, trial, and narrowed-ship record—not a claim that
> Process Engine provides Etsy API access or that the downstream package is
> fully runtime-qualified.
>
> **Privacy:** the shop identity and source URLs are retained only as the
> operator's supplied context. Buyer data, credentials, private worksheet
> contents, host data, and internal identifiers are not published here.

---

## Executive result

The operator asked Process Engine to update and refine an existing Etsy skills
family and persona so it could assist with online-business management and Etsy
SEO. The engine collected and synthesized the supplied material, revised the
package, and was later recorded as having a bounded native Turnstone object
deployment. The evidence does not prove that deployment satisfied the Ship gate.

The resulting package is useful for **analysis, drafting, translation,
worksheet-export analysis, prioritization, trend frameworks, and advisory
policy heads-ups**. The following capabilities were deliberately not claimed:

- authenticated Etsy Seller App/API access;
- live shop, listing, order, or storefront reads;
- live seller-taxonomy lookup;
- live Google Sheets reads or writes;
- publishing listings or changing shop settings;
- sending customer messages;
- purchases, inventory commitments, or any Etsy mutation.

The correct overall runtime-dependent Trial classification remains
**INCOMPLETE**, not FAIL: the executed cases passed, but unavailable required
capability categories were not proven.

## Operator intent and material collected

The interaction supplied the existing Etsy package plus the following material
and context classes:

1. an online-business-manager skills article;
2. the operator's ChummyThailand storefront URL as target context;
3. an article describing an autonomous Etsy operating model;
4. the shared `Online_Business_Worksheet_2026_Master-V3.0` as business-analysis
   context;
5. Etsy developer documentation;
6. Etsy Dev MCP documentation;
7. the `getSellerTaxonomyNodes` reference.

The engine treated these differently rather than copying them wholesale:
source material supplied techniques and requirements, the storefront supplied
domain context, the worksheet supplied point-in-time analytical inputs, and
the developer references informed capability-path design. The Etsy Dev MCP
path was recorded as **documentation/specification discovery**, not Etsy API
execution.

The objective was refined into an assistant-manager package that could help
with customer-message drafting, listing and SEO analysis, business and
financial analysis, trend interpretation, weekly prioritization, and
operator-controlled next steps. The target was retained as an aspirational
north star rather than a guarantee.

### Trial → Ship chronology

The original Trial record explicitly classified the overall result as
**INCOMPLETE** and stated that INCOMPLETE does not advance to Ship. A later
ship record described a narrowed analysis/drafting scope as Trial PASS and
recorded native deployment/read-back, but the evidence inspected here contains
no separate Pattern revision, exact-scope Review PASS, exact-scope Trial PASS
receipt, or operator decision establishing a new PASS chain for that narrowed
artifact.

Accordingly, the deployment read-back proves object persistence, not Ship-gate
compliance. This case study records the outcome as a **Process Engine
pipeline-contract failure** unless a primary receipt for the missing narrowed
Review/Trial chain is later produced. It must not be rewritten as a successful
narrow Ship.

The initial Review did not silently pass the draft. It identified seven concrete
findings, including unproven destination-skill absence, incomplete persona and
governance artifacts, ambiguous treatment of existing skills, abstract
capability declarations, missing financial-source precedence, insufficient
customer-message safeguards, and an under-specified trend-evidence standard.
The revised package resolved those findings and was re-reviewed PASS.

## Downstream package trial evidence

The recorded trial evidence exercised **12 behavioral cases**, all passing. It
was later described as supporting the narrowed scope, but the evidence
inspected here does not prove that these cases were rerun against a separately
revised exact narrowed artifact before Ship.

- customer-message uncertainty and missing-order-fact handling;
- SEO boundary behavior without ranking guarantees or unauthenticated API use;
- financial arithmetic and source/freshness labeling;
- trend escalation into a bounded, testable recommendation;
- policy and external-action boundaries;
- wrong shop/listing identity;
- Etsy capability escalation;
- financial-source conflict;
- buyer-data minimization;
- commitment safeguards;
- external-emission safeguards; and
- adversarial medical-claim handling.

Activation cases also passed for the OBM assistant, customer-message skill,
financial-analysis skill, and the combined SEO/taxonomy and trend-analysis
path. The recorded activation observations were:

- OBM assistant: should-trigger 2/2; shouldn't-trigger 3/3;
- customer messages: should-trigger 3/3; shouldn't-trigger 2/2;
- financial analysis: should-trigger 3/3; shouldn't-trigger 2/2;
- SEO/taxonomy and trend analysis combined: should-trigger 4/4;
  shouldn't-trigger 1/1.

One buyer-privacy case passed with an evidence-path caveat: the safeguard
behavior was supported, but a delegated context did not consistently resolve
the direct reference path. This is retained rather than erased.

## Runtime and deployment evidence

The later native Turnstone deployment record reports read-back of the
following objects:

- the existing Etsy manager persona was updated in place;
- six supporting skills were created and read back;
- each created skill was enabled and scanner-rated safe;
- a content-only prompt policy was created and read back;
- the advisory judge helper remained **not deployed** because its native
  creation path was not exposed in the execution context;
- existing Etsy skills were retained and not silently overwritten, disabled,
  or superseded;
- a reversible rollback path was recorded and not executed.

This proves native object persistence and read-back for the objects named in
that deployment record, not Trial/Ship gate compliance and not the unavailable
Etsy integrations listed above.

## Reference-retrieval limitation

The re-review explicitly recorded a reference-retrieval limitation. The
following operator-supplied or identified references were **not retrievable
through the available fetch/preview path** during the run:

- the ChummyThailand storefront page;
- the Medium autonomous-Etsy article;
- the `getSellerTaxonomyNodes` reference.

The package correctly did **not** assert these as proven evidence, and trial
fixtures must not represent them as verified sources without a later authorized
retrieval.

The root cause of each failure is **not proven**. Each could have been any of:

- unsupported page/URL behavior;
- authentication or permission scope;
- a transient network failure;
- a tool/adapter limitation;
- a malformed or redirected URL;
- source-side blocking;
- a retrieval timeout; or
- incomplete page extraction.

The strongest development signal from the run is that Process Engine should
record a compact per-material **receipt** covering identity, retrieval status,
path, timestamp, extracted claims, use disposition, and failure class, so that
partial retrieval is visible and recoverable rather than silently absorbed.
